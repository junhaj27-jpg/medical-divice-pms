# RA 플랫폼 무결성·접근·검증

## 구조와 기존 기능 재사용

이전 ERD의 MedicalDevice·ProductLot·RegulationDocument/Chunk·CAPA·SafetySignal·Recall/원장·ReportArtifact·BusinessPartner를 그대로 참조한다. 새 RA 유형은 각각 구체 테이블 26개이며 공통 추상 클래스는 물리 테이블을 만들지 않는다. WorkTask와 Attachment는 기존 사건 FK를 유지하며 RA 전용 기록의 경우 동일 테이블에서 제품 규제 프로필 FK를 사용한다. XOR CHECK로 정확히 하나만 지정한다. 가짜 사건이나 규정·승인·교육 수료 이력을 이관에서 만들지 않는다.

대상 23개 업무 종류의 입력 화면/JSON은 같은 검증 서비스로 저장한다. 모델의 직접 save는 서비스 경로를 요구하고 M2M 변경과 ORM 삭제도 앱에서 차단한다. 새 이력의 행위자와 관련 증빙·도메인 관계는 PROTECT를 사용한다. 신규 관계를 문자열/GFK로 바꾸지 않았다. 변경 사유·행위자·시각·수정 버전은 기존 append-only AuditLog, 허가 이벤트, 현장 연락/평가 등에서 추적한다. RA 업무 감사 AuditPlan은 시스템 감사 로그와 구분한다.

## 권한과 안전한 쓰기

- 활성 RA/QA와 ADMIN만 `/ra/`, 기록 조회·등록·편집·파일·JSON API에 접근한다. 직접 URL로도 서버에서 검사한다. STAFF는 기존 자기 업무와 본인 `/my-training/`만 볼 수 있다. 교육 파일도 배정 대상자와 해시를 검증한다. 현재 전문 역할은 전체 RA 프로필을 조회하므로 조직별 테넌트 격리로 표현하지 않는다.
- 초안 → 검토 요청 → 지정 검토자(또는 ADMIN) 검토 완료 → 작성자와 다른 ADMIN 승인. 문서/제품 버전/표시/현장 조치에는 시행 단계, 변경에는 승인 후 실제 시행 확인, 감사/조치에는 종결 조건을 둔다. 취소·폐기에는 사유를 보존한다. 인허가의 외부 상태는 내부 승인 상태와 별도로 기록한다.
- 불변 승인 내용은 해시와 대상 버전, 당시 연결 파일의 ID/경로/해시, 제품/국가/조직·관련 기록 요약을 포함한다. 승인된 문서·제출본은 수정하지 않고 새 버전을 만든다. 정책적으로 재검토가 필요한 현재 상태 기록은 별도 reopen 동작으로 초안으로 되돌리고 이전 승인 이벤트를 유지한다. 업무 완료와 수동 시행 확인은 승인 대상 내용과 별도 운영 사실이다.
- 부모 규제 프로필 → 자식 행 순으로 PostgreSQL `select_for_update`를 요청하고, 폼의 수정 버전으로 stale 편집을 차단한다. 문서/라벨의 동시 시행은 부분 고유 제약을 사용한다. 대상/수량/일자/역할 상태 범위·유일성은 가능한 부분을 CHECK/unique로 보장한다. 교차 모델의 같은 제품·예시·관할·조직 관계와 파일 상태는 서비스 검증이다.
- 개인정보를 자유 서술·제출 파일에 불필요하게 넣지 않는다. 교육은 사용자 FK, 감사 추적은 행위자 FK를 사용한다. 개인을 식별하는 환자 원문은 신규 RA 모델에 별도로 복제하지 않는다. 파일 본문은 기존 비공개 Attachment 저장소에 한 번 저장한다. 패키지 ZIP은 다운로드 시 메모리에서 생성하고 추가 저장하지 않는다(파일 100개/총 50MB 제한). 파일 형식과 해시 검사와 실제 악성코드 검사는 별개다.
- 보존 정책은 조직·범주·근거·확인일·기간·파기 검토 절차를 기록한다. 자동 삭제는 비활성 고정, 실제 파기 기능 없음. DB 해시/로그는 법적 전자서명이나 변조 불가능한 스토리지가 아니다. `QuerySet.update`/`bulk_create`/SQL과 저장소 관리자 접근은 앱 보호를 우회할 수 있으므로 별도 권한으로 제한한다.

## API와 범위

세션 인증 및 CSRF가 적용된다. `GET /ra/api/<종류>/`는 최신 200개 요약, `GET /ra/api/<종류>/<id>/`는 내용·승인 스냅샷을 반환한다. 같은 URL에 `POST {"data":{...},"reason":"...","revision":2}`로 등록/수정한다(신규 등록은 revision 불필요). 수정은 폼과 동일한 전체 입력이며 PATCH가 아니다. 외래키는 PK, M2M은 PK 배열을 보낸다. 상태·스냅샷 같은 시스템 필드는 쓰기 금지다. `POST {"action":"submit","reason":"...","revision":2}`로 지원되는 수명주기 동작을 처리한다. 시행/후속 결과의 확인 내용은 `details.confirmation`에 보낸다. 삭제는 405다. JSON API는 기존 DRF/OpenAPI 라우터와 별도의 세션 API다. 파일 등록·현장 연락·교육 일괄 검토·정기 캡처는 HTML 및 해당 서비스로 제공된다.

RA를 도입해도 기존 PMS 승인 해시 버전과 사례 범위는 그대로다. 교육에 의한 제한은 담당 조직이 승인한 TrainingRequirement에서 명시적으로 켰을 때 새 RA 승인에만 적용하며 기존 PMS 승인·역할을 변경하지 않는다.

## 마이그레이션과 검증 방법

- 0016: 규제 프로필/요구사항/인허가/제출과 기존 업무·첨부의 문맥 확장. 기존 행은 `complaint_id`를 보존하며 `ra_profile_id=NULL`이다. 기존 complaint 필수 조건 때문에 새 XOR 제약 도입 전의 정상 레거시 행은 조건을 만족한다.
- 0017: 제품 버전·변경·통제 문서·라벨. 0018: 제품 위험·외부 정보·현장 조치·공급자. 0019: 교육·감사·경영 검토·보존 정책. 0020: 제출의 변경/제품 버전 연결 및 도메인 제약. 0021: 교육 시도 번호/유일성. 앞선 0001~0015를 수정하지 않았다.
- 실제 운영 데이터와 원본 사용자 DB에 적용하지 않았다. 0015 상태의 역사 모델로 합성 사례·업무·첨부를 만든 다음 전진 적용하는 회귀 테스트에서 PK·문맥·파일 경로 보존 및 임의 RA 프로필 미생성을 검사했다. 새 DB 설치도 별도로 실행했다.
- 규정 원문의 공식성·최신성을 자동 검증하지 않으며 이번 작업에서 실제 기관별 법적 요구사항을 등록하지 않았다. 공식성 확인이 없으면 확인 필요로 남긴다. 외부 AI·메일·기관 시스템을 호출하지 않았다.

## 실무 확장 마이그레이션

- 0022는 GMP, 품질시스템 밸리데이션, 회의록·DHF, 변경심사, 보안 추적 테이블을 추가한다.
- 0023은 회의록 파일 후보, 템플릿 원본 및 제출 검토 목록을 추가한다.
- 0024는 양식 정의, 시험 버전, 회의록 원본 및 기술문서 목차의 중복 키를 보호한다.
- 기존 제품 버전, 통제 문서, 제출 패키지, 증빙, 업무 및 승인 서비스는 계속 사용한다. 이전 레코드를 새 테이블로 변환하거나 자동 보완하는 데이터 마이그레이션은 없다.
- QA 기록과 제품 검증 문서의 추적 경로를 구분했다. 승인된 후보의 원문과 연결 결과, 밸리데이션 실행과 재시험, GMP 정정은 별개 행 또는 승인 스냅샷으로 보존한다.
- 업무 기한과 사용자 작성 상태는 플랫폼 기록이다. 규제 판단, 사이버보안 적합성 및 품질시스템 수용 여부는 담당자가 입력하고 검토한다.

0021 스키마의 합성 규제 프로필과 통제 문서를 0024까지 전진 적용해 기존 PK, 제품 연결, 문서 본문이 보존되고 임의 GMP 기록이 생성되지 않음을 확인했다. 기존 사건·업무·첨부를 포함한 0015 전진 적용 회귀 테스트도 실행했다.

전체 실행은 마지막 업무/증빙 게이트 및 출시 버전 출력 보완 전에 시작했다. 해당 변경은 이후 37개 대상 실행과 출시 버전 고정 이후 5개 실무 실행으로 확인했다. 실행 로그는 work/ra-platform의 ops-full.log, ops-final-target.log, ops-export-tests.log, ops-forward.log에 있다.

실제 PostgreSQL 동시성, 운영 데이터, 외부 악성코드 검사기 동작은 미검증이다. 파일 관련 테스트는 합성 파일에 검사 통과 상태를 구성한 뒤 실제 바이트와 해시를 확인했다. 공식 규제 기준 등록, 외부 제출, 외부 AI 연동, 배포 및 push는 수행하지 않았다.

후속 점검에서 공백만 입력한 GMP 필수 값도 누락으로 처리하고, DHF 매트릭스에서 통제 문서의 대표 파일을 증빙 목록에 포함하도록 보완했다. 중복 파일 제거와 공백 판정을 직접 검증했고 Django check 및 git diff --check를 통과했다. 위 전체 회귀 결과는 이 두 보완 전 실행이다.

GMP 작성 기록에는 DHF 프로젝트를 직접 연결할 수 있다. 연결은 기존 RA 서비스의 동일 규제 프로필 검사 대상이며 기존 기록은 프로젝트 미지정 상태로 유지된다. 격리 SQLite에서 0024 → 0025 전진 적용, Django check 및 마이그레이션 누락 검사가 통과했다.
